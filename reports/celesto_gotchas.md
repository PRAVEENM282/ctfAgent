# Celesto Phase 0 gotchas

## SDK and basic lifecycle

- Installed and pinned `celesto==0.1.7` for this probe. The public `Computer` signatures are recorded in `reports/evidence/phase0_echo.log`.
- Version history: with `celesto==0.0.14`, the stock `celesto computer list --json` called `GET /computers` and got HTTP 404. Upgrading in place to 0.1.6 made the adapter raise a bare `ValueError`; the old probe swallowed the traceback, so the root cause remains unknown. See `DECISIONS.md`.
- `Computer(provider="cloud")` passed the guarded `echo hi` smoke. `Computer.delete()` was followed by an independent `Computer.get(id, provider="cloud")` check; the deleted ID raised `VMNotFoundError`.
- `celesto computer list --cloud --json --all` is rejected by this CLI. Use `--limit 100`.
- The SDK reports `possibly_truncated=true` even with zero returned rows. Its inspected implementation sets this flag when `len(rows) >= limit or response.count >= len(rows)`; the list API exposes no offset/cursor. A zero-row page does not prove the whole account inventory is empty. The reaper checks each tracked ID directly and does not delete IDs it does not own.
- The public `Computer` API and `celesto` module have no public member/export containing `hook`. The 0.1.7 CLI does include `doctor`.
- `celesto doctor` exits 1 in the API container because it invokes `sudo`, which is not installed there. The full redacted output is in `reports/evidence/phase0_sdk.log`.
- On the host, `celesto doctor --backend firecracker --json` using the latest isolated PyPI SDK completed with exit 0, zero failures, and four warnings. Its host paths were redacted in `reports/evidence/phase0_sdk_host.log`; this is separate from the API-container failure.

## Create options and persistence

- The 0.1.7 `ComputerCreateRequest` model exposes `size_id`, `vcpus`, `ram_mb`, `disk_size_mb`, `image`, `template_id`, `template_version`, `network_policy`, and `external_volume_enabled` (plus generated `additional_properties`). `network_policy.mode` has `OFF` and `OPEN` values. The model documents `external_volume_enabled` as attaching persistent storage at `/home/ohm`, disabled by default. The installed `CloudProvider` constructor exposes the sizing/image/template fields and `external_volume_enabled`, but not `size_id` or `network_policy`; those two are present in the generated request model only. Model presence does not establish account acceptance.
- The Phase 0 network-policy probe first received HTTP 403 with `X-Celesto-Experimental: true`; no computer was created. Omitting that header returned HTTP 201. The project now sets `network_policy=off` inside `CelestoAdapter` through the generated request model, after requiring exact SDK version 0.1.7; it refuses to create if that path is unavailable and does not fall back to egress-on. Live project-code evidence shows the per-attempt curl blocked with exit 28 while a published inbound marker returned HTTP 200; same-ID app restart, endpoint revoke to HTTP 404, SIGINT, and confirmed delete passed. Evidence: `reports/evidence/m3_live_lifecycle.log`.
- The pinned Python `celesto==0.1.7` public Cloud constructor lacks `network_policy`, so this project uses its exact-pinned generated Cloud request model inside `CelestoAdapter`. Official sources are currently not sufficient to claim that a public Python setter is supported on Cloud: the `CelestoAI/sdk` README shows `Computer(network_policy={"mode": "off"})`, while the current PyPI 0.1.8 docs describe `internet_settings={"mode": "off"}` in a Linux Firecracker context without identifying Cloud support. This project has not installed or live-validated 0.1.8; keep the 0.1.7 path until the Cloud API support and a deliberate upgrade are confirmed. See [Celesto Python SDK repository](https://github.com/CelestoAI/sdk), [Celesto 0.1.8 on PyPI](https://pypi.org/project/celesto/0.1.8/), and [Celesto sandbox docs](https://celesto.ai/sandboxes).
- Live provider responses expose `price_version=usage-v2`, but no dollar rate. Use Micro at $0.015/hour from the brief/rate card and label it `computed_from_duration`; persist billable `celesto_duration_s` separately from wall time, excluding intervals after stop completes and before resume begins. The lifecycle log records the final duration and derived charge.
- A clean scratch venv and a separate `/tmp` venv in the API container both resolved the latest PyPI package to 0.1.7, the existing pin. `Computer`/`CloudProvider` constructors still reject `persistent_home` and `network_policy`; `network_policy` appears in the generated request model but not the public `CloudOptions`. `Computer.lifetime` is stored by the wrapper and is not passed to the cloud request. Do not change the pin based on the current docs alone. See `reports/evidence/phase0_sdk_latest.log` and `phase0_sdk_lifecycle.log`.
- The cloud template catalog reports `scratch` at 7,168 MB disk / 512 MB RAM, with shell, curl, and sudo; `coding-agent` is 15,360 MB / 1,024 MB and includes Python, pip, uv, and Node. Catalog output is in `reports/evidence/phase0_template_catalog.log`; actual guest measurements are in the runtime probe logs.
- A scratch guest booted in 25.033s and reported no Python or pip, one CPU, 2,021,228 kB memory, and a 21,118,275,584-byte root filesystem. The catalog's advertised defaults and guest-reported filesystem/memory sizes differ, so keep the two kinds of evidence separate. A request combining `template_id="scratch"` with `image="ubuntu-desktop-24.04"`, `vcpus=1`, `ram_mb=512`, and `disk_size_mb=7168` returned HTTP 422 (Request ID `f4d60484db0c254be31cad80662c66d1`). Immediate raw list reconciliation returned HTTP 200, count 0, no rows. The error did not identify the offending field. See `reports/evidence/phase0_template_scratch.log`, `phase0_template_small_shape.log`, and `phase0_small_shape_reconciliation.log`.
- `Computer(..., lifetime="persistent")` is accepted, but in 0.1.7 `lifetime` is a wrapper lifecycle/context-manager setting and is not passed to `CloudProvider` or the cloud create request. That create sends `external_volume_enabled=False` by default. Its acceptance therefore did not test cloud storage persistence. `external_volume_enabled=True` alone returned HTTP 422 with `side_effects=none`; the combined request also returned HTTP 422 with no validation details. See `reports/evidence/phase0_persistence.log` and `reports/evidence/phase0_sdk.log`.
- The CLI's `computer create --help` is local-computer oriented and has no cloud persistent-lifetime or external-volume flag. Browser access (`Computer.browser()`, returning a CDP WebSocket connection) and published ports are separate operations, not fields on `ComputerCreateRequest`. Browser responses contain a gateway URL, token, and expiration; port publishing uses `port` and `force` in its own request model. See `reports/evidence/phase0_sdk.log`.

## Published ports and ephemeral lifecycle

- An ephemeral cloud guest published port 8000; `published_ports()` returned the same URL and the URL served the test marker over HTTP 200. Removing the route-host component from the URL returned HTTP 301 without the marker; this checks only that URL shape, not broader authentication semantics.
- Ephemeral `stop()` and `resume()` both returned successfully with the same computer ID. The port stayed listed with the same URL, while the URL returned 502 because the probe server process was not running after resume. Unpublish removed the port from `published_ports()` and the old URL returned 404.
- A `coding-agent` guest created with `lifetime="ephemeral"` retained its port route and URL through same-ID stop/resume. The probe restarted its Python server after resume; the same URL returned HTTP 200 with the marker before and after resume. Unpublish removed the route and the old URL returned 404; deletion was confirmed in 6.395 seconds. This completes the Phase 0 provider-level `published_ports` gate; the learner pause/resume manager flow belongs to M6. See `reports/evidence/phase0_published_ports.log`.
- The old `protected=true` probe label was incorrect: removing the route host returned 301, which is evidence of host routing only. Current output uses `HOST_ROUTING_RESULT host_routing_observed=...`; the public URL remains unauthenticated.
- Port removal may take time to appear in inventory: the first no-server attempt still listed the port on its immediate recheck; the later probe observed it absent after five polls.
- Cleanup was delayed: Celesto inventory and targeted lookups initially reported the tracked guest as `deleting`, and the reaper's delete retry timed out. A later direct lookup raised `VMNotFoundError`; the normal reaper then printed `ALREADY_ABSENT` and cleared its local registry entry. `reports/evidence/phase0_cleanup_retry.log` records both the timeout and final confirmation.
- The initial HTTP-server attempt used `python3`, which is absent from the image; the successful probe used the guest's existing Perl and `IO::Socket::INET`. The first Perl-free probe still verified publish/list and same-ID stop/resume, then confirmed its guest deletion. See `reports/evidence/phase0_published_ports_no_python.log` and `phase0_published_ports.log`.
- On the `coding-agent` template, the guest reported Python 3.12.15, pip 26.2.1, and SQLite 3.53.1; measured root filesystem size was 21,047,758,848 bytes, with one CPU and 2,021,228 kB reported memory. Boot-to-ready took 15.079 seconds. `scratch` was measured separately and does not include Python; its catalog defaults are not equal to the guest's reported root filesystem size or memory.
- A later persistent-template create returned HTTP 503 with an ambiguous outcome. A direct account list then returned count 0 and no rows; a single retry created and deleted the guest successfully. See `reports/evidence/phase0_persistent_port_503.log` and `phase0_503_reconciliation.log`.
- `scripts/reap_orphans.py` now retries `ReadTimeout` and `ConnectError` up to three attempts with 1s/2s backoff, then polls direct ID lookups until `VMNotFoundError` or a bounded timeout. Confirmed delete logs include elapsed time and poll count. Unit tests are in `tests/test_reap_orphans.py`.

## LLM and account limits

- The real five-call smoke passed against pinned `openai/gpt-oss-120b` through the configured Groq endpoint; every response matched and totals were 380 prompt, 80 completion, and 460 total tokens. Evidence: `reports/evidence/phase0_tool_call_smoke.log`.
- Groq's public Free Plan table lists this model at 30 RPM, 1,000 RPD, 8K TPM, and 200K TPD; exact organization limits may differ. With 20 LLM iterations and 3 provider retries per call, the configured upper bound is 80 provider HTTP requests per logical attempt. Twenty clean attempts could reach 1,600 requests; 20 logical jobs exhausting both outer retries could reach 4,800, plus the five-call smoke. This worst case does not fit the public baseline. M5 must enforce retry-inclusive budgeting, use a provider/plan with enough daily requests, or lower the request ceiling and confirm the account-specific limit before batching. See [Groq rate limits](https://console.groq.com/docs/rate-limits).
- The trial start date was not returned by CLI/API checks. The browser dashboard could not be read in this run; do not infer the date.
- The live trial rejected a second retained guest with HTTP 429 `trial_retained_sandbox_limit_reached`, `side_effects=none`; this confirms the one-retained-guest limit for the account. No concurrency test was run.
- M7's initial attempt to create an egress-open guest while the published egress-off receiver still existed returned HTTP 429 `trial_retained_sandbox_limit_reached`, `side_effects=none`. The harness was changed to delete the first guest and run the positive control sequentially. The egress-open guest passed `curl https://example.com`, and its published receiver was healthy from the control plane, but a POST from that guest to its own published URL returned curl exit 22 and the receiver count stayed zero. The exact HTTP status was not recorded. Both guests, routes, and cleanup were verified. M7 remains incomplete because a positive receiver path from an egress-open guest has not been established; see `reports/containment.json` and `reports/evidence/containment.log`.

## M3 live implementation notes

- The first two project-code lifecycle attempts failed closed after the original default audit path under `/app` could not be written by the non-root container user. Because the old audit append happened after dispatch, whether the curl command ran is unknown; no raw result was captured. Both guests were independently deleted. The adapter now defaults to the writable persistent state volume and opens audit storage before dispatch, so unavailable audit storage prevents execution. Their historical run rows have unknown cost and retain `NULL`; do not estimate it.
- One later attempt passed egress verification but the guest HTTP launcher returned exit 2; that guest was revoked and deleted. The launcher now uses a foreground Python parent and detached server process. The final timing-rich lifecycle run is `reports/evidence/m3_live_lifecycle.log`.
